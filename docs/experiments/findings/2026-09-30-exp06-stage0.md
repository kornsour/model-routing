# 2026-09-30 · exp06 Stage 0: headroom calibration (15 tasks × Haiku 4.5 / Sonnet 5.5 / Opus 5.5 × 3 trials)

Real run on the Claude track (`exp06_calibrate`, subscription login, Claude
Code 2.1.285, harness `d30a822`, resumed once on `c40a1b6` after a planned
stop at a cell boundary), task set `tasks/exp06/tasks.jsonl` (hash
`e2f1de4a3ba9…`, commit `82c0230`), randomized block order, 40-turn cap,
3 trials. 135 graded cells, **$51.34** list price. The CLI's own reported
cost matched the harness's price table to the cent on every session.

This is Stage 0 of exp06 (`docs/paper/exp06-route-on-evidence.md` §7.1): it
measures whether the frontier model can do work the mid-tier model cannot
(gate **H0**). It is exploratory; nothing was registered.

## The task set

Fifteen tasks written for this study before any model saw them, in two new
stdlib-only fixture repos, each with a reference solution and hidden tests
(the untouched repo fails them, the solution passes):

- **`toolbelt`** (8 tasks): implement or repair a module to a written spec
  (npm semver ranges, RFC 6902 JSON Patch, Vixie cron with DST, glob with
  globstar/braces/dotfiles, unified-diff application, ISO 8601 durations,
  INI inheritance and interpolation, exact money allocation and formatting).
- **`orchestra`** (7 tasks): a deterministic job-DAG scheduler with a
  specified run loop; tasks add trigger rules, fix interacting retry bugs,
  migrate a storage format across three versions, make the loop scale to 20k
  jobs without changing a single decision, add cancellation, add reservation
  and priority aging, and add critical-path planning.

Briefs median about 780 tokens (range 430–1,030), between real `spawn_task`
chips (about 500) and subagent dispatches (about 1,100) in the chip harvest.
The tasks were built to be hard: long specs where one missed clause fails
the hidden tests, performance traps (catastrophic regex backtracking,
quadratic loops), bit-exact behaviour preservation, DST edge cases.

## Result: no headroom, H0 not met

| model | passed | cost | cost per completed task (95% CI) | median turns | turn-capped |
|---|---:|---:|---:|---:|---:|
| Haiku 4.5 | 12/45 (27%) | $17.41 | $1.45 ($0.82–$3.92) | 38 | 21 |
| Sonnet 5.5 | 44/45 (98%) | $11.61 | $0.264 ($0.233–$0.297) | 9 | 0 |
| Opus 5.5 | 45/45 (100%) | $22.33 | $0.496 ($0.448–$0.545) | 8 | 0 |

Measured labels (§7.1): **easy 14, medium 1, hard 0**. H0 needs at least 10
measured-hard tasks. Not one task was passed by Opus and failed by Sonnet.

Sonnet's single failure (`tb-cron-03`, trial 2) returned a generator from
`iter_fires` where the hidden tests compare with a list. The brief said
"returning the next `count` fire times in order", so this is a strict-grader
miss on an ambiguous sentence rather than a capability gap.

The only headroom on this set is **Haiku to Sonnet**, and it does not pay:
Haiku burns most of its 40-turn budget on the tasks it fails, so a perfect,
free Haiku-then-Sonnet trigger would cost **$0.596 per completed task, 2.3×
always-Sonnet**, for the same completion. That repeats the companion
study's finding one model generation later.

## Side finding: the 5.5 models are about a third of the cost of 5.0

The run was first started on Sonnet 5 / Opus 5 (the CLI aliases on 2.1.278)
and stopped after 14 cells when the study moved to the current models (all
14 passed; kept as `results/exp06_calibrate/20260929-201525-v5.0-aborted`).
On the seven tasks both generations ran:

| | Sonnet 5 → 5.5 | Opus 5 → 5.5 |
|---|---:|---:|
| cost | $6.20 → $1.83 (0.30×) | $12.61 → $3.77 (0.30×) |
| turns | 198 → 84 | 215 → 80 |
| output tokens | 241k → 72k | 185k → 87k |
| prompt tokens | 10.3M → 2.3M | 9.3M → 2.4M |

Per-task means; one 5.0 trial per task against three 5.5 trials. The CLI
version also changed (2.1.278 → 2.1.285), so the saving belongs to model and
harness together. Completion was 100% on both sides. Most of the saving is
fewer turns re-reading the growing context, not the lower Opus 5.5 price.

## What follows

Under the protocol's stopping rule H0 has failed once; one extension with
more tasks is allowed before the result stands. The ladder arms are run
anyway (exploratory) to measure what the ladder costs on work where it has
nothing to earn: L1 condition 2 (easy-stratum cost against always-Sonnet)
and how often it escalates without need. See the exp06 results paper.
